2026-09-20 三处修订（回应张老师的三个疑问）

① 文件名为什么还叫 manhua.py？—— 刻意埋的伏笔，已坐实。 上版把电商写成 Product、漫剧写成 Character(Product) 子类，文件却叫 manhua.py，逻辑是反的。正确埋法：电商是底座，漫剧角色是 Product 的一个子类。文件名的"彩蛋"是期末学生发现"原来漫剧角色就是电商商品换了个子类"——这条管线换一个 Product 子类就能做漫剧。名字保留，伏笔在代码与本文坐实。

② 上次代码不完整？—— 已补全，三处假桩现在真干活。 旧版 consistency_score 写死返回 0.8（没体现 OOP 价值）、pick_best 永远传 {"face_ok":True}（阈值形同虚设）、deliver 只写一行 README（无真实交付结构）。新版：打分用白底纯度/构图/清晰度/文字占比的可判定公式；筛选对每个候选真算分；交付按 SKU 分文件夹、带废片率/成本/耗时。

③ 真实感怎么保证？—— 不冒充客户，但每个字段贴真实运营口径。 平台规范（淘宝 800×800 白底、拼多多禁用绝对化用语、抖音不得含二维码等）来自 2025-2026 各平台商家后台公开要求；SKU 清单是"脱敏改写自真实类目"的示例 brief（某陶瓷文创店双11素材需求），含白底主图/场景图/细节图三类、多平台、真实卖点与材质。基础层不必是真实项目，但场景必须像真的。

2026-09-20（续）两处调整 · 回应"零件一词怪 / 原课程怎么接"

① "零件"→"构件"。 "零件"偏拼装玩具感。正式术语改为构件（component）——软件工程里指"可独立开发、验证、最终拼装成完整系统的构建块"，正好对应"每章给一个文件加一块、期末拼成整条管线"。同文档内"十一个构件"已统一。备选词：增量（强调逐章累加）/ 里程碑（强调章节节点），若您更顺口可一键替换。

② 补"原课程无缝嫁接"专章（见第五节）。 核心结论：原课程语法内核 100% 保留（章节顺序、知识点、考点都不动），改造只发生在"上机实验"层——把每章孤立习题换成"给同一个项目加一个构件"。理论不变、实验换载体，所以无缝、不增课时。

一、manhua.py 到底是什么

一句话定义：manhua.py 是 Python 课整学期唯一的项目文件——不是"一个项目"，是"一个脚本"。学期开始时它几乎是空的，每章只加一个"构件"，学期末它是一个能跑通电商素材管线的完整脚本。

最终形态（读一份 SKU 清单 → 批量调图生接口 → 自动筛废片 → 输出合格素材包 + 生产记录）。学生交的就是这一个文件 + 它的 runs/ 和 deliverables/。原教材的"飞机大战项目"被它更高达成度地接走。

为什么是"一个文件"而不是"一个项目"：提速的真正来源不是讲得快，是不重复——每章的背景解释只需 5 分钟，因为学生已经认识这个脚本；作业产生复利（上一章的代码这章接着用），而非每章从零写练习。

载体说明：9-19 决策后，主线载体从漫剧 Character 类换成电商素材管线 Product 类（白底图+材质色彩规范+多角度参数+质检标准）。Character 类降为进阶选修实例（"同一个类的两个实例"）。本文件已按 Product 版写。

三、与二级训练营的衔接（核心）

3.1 衔接的根本逻辑：课内教"分叉之前的那段"

两条赛道（电商 / 漫剧）共享的八成主干（B1 批量并发 / B2 一致性 / B3 归档版本 / B4 质检筛选 / B5 工作流封装）在二级才展开。课内 60 学时教的，正是"分叉之前的那段"：连接器（调接口/批处理/Git/读报错）+ 一个能跑的单件脚本。所以课内不必在两条赛道间二选一——学生带着的是那八成主干，二级再分流。

课内 manhua.py（单件脚本）→ 二级 B1-B5 放大成工程能力→ 三级 真实交付 + 生产记录

3.2 时间衔接：课内打底，训练营第 4 周启动，第 12 周合流

  • W1–11 课内：打语言底座，manhua.py 长到构件 7（前 8 周全是 mock，无真实调用）。
  • W4 训练营启动：前 8 周不写代码（出图/一致性/分镜用现成界面），与课内进度无关，反而是给课内攒问题的地方。
  • W12 合流：课内讲"调接口"（构件 8），训练营此时介入代码——学生已经知道"为什么调接口"，不会把它当又一章孤立知识。

关键设计：模块 A（调接口）提前到第 12 周，不等章节讲完。原因：调接口是后面所有内容的引擎，太晚讲前面只能一直 mock，学生会失去真实感。放在第 12 周正好接在第 8 章类 + 第 9 章异常之后：参数已能组织好、失败已能处理，一次就成。

3.3 能力对齐：同一条线被放大三次

能力线一级（课内 manhua.py）二级（训练营 B1-B5）三级（核心项目组）

结论：三级不是新东西，是二级同一条能力线被放到真实交付里；二级也不是新东西，是课内单件被放大成批量与工程化。衔接不是"教两遍"，是"同一根线越拉越粗"。

3.4 衔接的"接口"：文件契约 CONTRACT.md

课内 manhua.py 跑出的 results/ 目录结构，就是与训练营（及未来 JS 工具组）对接的契约原型：

results/
  task_xxx/
    raw/        # 候选图
    picked/     # 筛选后合格图
    meta.json   # task_id / status(done|failed|pending) / files / attempts / seconds / cost

二级 B3 直接复用这个结构做版本与归档；若后续 JS 班进工具组，meta.json 的字段就是双方契约（字段只增不改 / status 必须三态 / 相对路径）。课内第 5 构件写的归档，天然就是契约的雏形——这是衔接最省力的一点。

3.5 7-8 人核心如何"带过去"（对应 9-19 规模决策）

  • 课内是全体 Python 班必修底座（不淘汰）；7-8 人是自组织的高质量核心，从课内自然分层出来（不以开营就圈"重点"）。
  • 这 7-8 人把 manhua.py 的构件带进二级，自己放大成批量/一致性/质检，并自组织成"电商管线组 + 资产与规范组"。
  • 二级失败判据（第 8 周自查）：学生能否独立跑完"需求进来 → 素材出去 → 有记录"。能，就进三级；不能，说明二级滑成兴趣小组，三级长不出人。这条判据正好用课内 manhua.py 当样本。

5.1 嫁接根本原则：不砍知识点，只换实践载体

  • 语法内核 100% 保留：原课本的章节顺序、每个知识点、期末考点全部不动。考试仍按原知识点出（比如仍可单独考"写一个学生类"）。

  • 理论不变 + 实验换载体 = 无缝：老师照常按课本讲理论，学生照常做实验，只是实验产物不再是一次性练习文件，而是同一个项目的累积增量。不需要额外重排课表。
