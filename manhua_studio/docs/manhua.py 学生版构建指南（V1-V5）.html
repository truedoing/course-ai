manhua.py 学生版构建指南（V1–V5）

一份「对着它写代码」的任务书 —— 讲清楚这个项目是什么，然后把每个版本拆成「你要写什么功能 / 函数契约 / 验收标准 / 怎么向 AI 提需求」。

AI 辅助 · 一步一步写 GitHub v1–v5 仅作范本对照

1. 这个项目是什么（先建立整体直觉）

manhua_studio（课程里叫 manhua.py）是一条「电商素材出图管线」。它干一件事：把商家随手拍的一张商品实拍照片，一步步变成能上架的素材——

  • S1 去底：照片 → 抠掉背景 → 白底主图
  • S2 出图：白底图 → 放进不同场景 → 多张场景图
  • S0 识别：照片 → 自动认出是什么商品、写卖点文案
  • 再叠加：质检筛选、WebP 压缩、归档日志、商品页数据

这些能力被拆成 11 个「构件」，串在一条主线上：连接器 → 批处理 → 一致性 → 质检 → 文件契约。每个版本（V1→V5）只往上加一层能力，所以每版都不大、都能跑通。

为什么要一步一步写，而不是直接用现成工具？ 练的是「工程化能力」：怎么把一个含糊需求翻译成可运行、可复用、可交付的代码。这正是高职生相对「纯用 AI 工具的人」的护城河——你既能用 AI，也能把 AI 的产出工程化交付。

2. 环境与骨架（做一次，V1–V5 共用）

2.1 安装依赖

pip install requests python-dotenv Pillow

2.2 包结构（从 V1 第一天就按这个搭）

course-ai/
├── env.example          # 密钥模板（复制成 .env 填值）
├── .env                 # 你的密钥（不进 git）
└── manhua_studio/       # ← Python 包，所有代码在这里
    ├── __init__.py      # 加载 .env + 版本号
    ├── schemas.py       # 数据结构 / 异常
    ├── adapters.py      # 外部服务适配层（S0/S1/S2）
    ├── prompts.py       # 提示词模板（V2 起）
    ├── pipeline.py      # 业务管线（V3 起）
    └── cli.py           # 入口（解析参数、调度）
运行方式（固定）： 在 course-ai/ 根目录执行 python -m manhua_studio --input 照片.jpg。
禁止 python manhua_studio/cli.py 直接跑——cli.py 用了包内相对导入，裸脚本执行会 ImportError。git 与运行都以父级 course-ai 为工作区。

2.3 密钥（.env）

  • UAPI_KEY：S1 去底（uapis.cn 免费申请），V1 起就需要。
  • ARK_API_KEY：S0 识别 + S2 出图（火山方舟），V4 起需要。
# env.example
UAPI_KEY=你的_uapis_密钥
ARK_API_KEY=你的_火山方舟_密钥

布置：cp env.example .env 后填入真实值。.env 已被 .gitignore 忽略，不会进提交。

3. 你在 AI 辅助下怎么写（工作模式）

  1. 读版块：先看本指南某一版的「目标」和「你要写的文件」。
  2. 向 AI 提需求：把「函数契约」里的输入输出讲给 AI，让它写实现。例：「写一个函数 stage1_remove_bg(input_path, api_key)，调用 uapis 抠图接口，把返回的白底图存到 assets/素材/ 下，返回本地路径。」
  3. 你跑、你看：复制 AI 给的代码，自己运行，自己读报错。
  4. 验收过关：对照本版「验收标准」逐条核对，跑通再进下一版。
  5. 对照范本（可选）：真卡住了，去看 git show vN:manhua_studio/xxx.py 的对应版本——那是答案，不是起点。
AI 是「副驾」，你是「驾驶员」。代码归你写、归你跑、归你负责。本指南给的是契约和边界，不是完整答案。
V1

去底白图 —— 照片 → 白底商品图（S1 去底）

对应阶段：S1 去底。这是地基，只做一件事，但必须端到端跑通。

目标

给定一张商品照片，调用免费的 UAPI 抠图接口，去掉背景、输出一张白底商品图，存到本地。命令行：python -m manhua_studio --input 照片.jpg。

你要写的文件（4 个）

① manhua_studio/__init__.py —— 包初始化 + 加载密钥
  • 显式加载 .env：优先找包目录下的 .env，其次找运行目录下的（哪个存在用哪个）。
  • 定义 __version__ = "1.0"。
# 契约要点：
from pathlib import Path
from dotenv import load_dotenv
_env_path = next(
    (p for p in (Path(__file__).resolve().parent / ".env",
                 Path.cwd() / ".env") if p.exists()), None)
if _env_path is not None:
    load_dotenv(_env_path, override=False)
② manhua_studio/schemas.py —— 异常类（V1 只有一个） 
class GenerationError(Exception):
    pass
③ manhua_studio/adapters.py —— 外部服务适配层（V1 只有 S1）
  • 常量：UAPI_ENDPOINT = "https://uapis.cn/api/v1/image/matting"
  • 辅助 _ensure_dir(p)：目录不存在就建。
  • stage1_remove_bg(input_path, api_key) -> str：内部调 _call_uapi_matting，返回本地白底图路径。

UAPI 抠图请求契约（必知）：

POST https://uapis.cn/api/v1/image/matting
Headers: Authorization: Bearer <UAPI_KEY>
Body(form):
  image_base64 = "data:<mime>;base64,<图片base64>"
  image_name   = 文件名
  output       = "background"
  background_color = "ffffff"   # 白底
  out_format   = "png"
返回 JSON: { "image_base64": "<白底图base64>" }
存盘: assets/素材/<原名>_whitebg.png
④ manhua_studio/cli.py —— 入口
  • argparse 解析 --input（必填，商品照片路径）。
  • 先校验：照片是否存在；UAPI_KEY 是否配置（没配就明确报错退出，别假装能跑）。
  • 调 stage1_remove_bg，打印「[完成] 白底图: 路径」。
验收标准（全部满足才算 V1 过关）：
  • python -m manhua_studio --input 某照片.jpg 不报错。
  • 生成 assets/素材/某照片_whitebg.png，肉眼看是白底、主体去背的图。
  • 没填 UAPI_KEY 时，给出清晰中文报错（不是一堆英文 traceback 甩脸）。
向 AI 怎么提（V1 范例）：
「帮我写 manhua_studio 这个 Python 包。① __init__.py 用 python-dotenv 显式加载包目录或运行目录下的 .env，定义 __version__='1.0'；② schemas.py 里定义一个 GenerationError(Exception)；③ adapters.py 里写 stage1_remove_bg(input_path, api_key)，内部 POST uapis.cn 的 image/matting 接口（Bearer 认证，传 image_base64、output=background、background_color=ffffff、out_format=png），把返回的 image_base64 存成 assets/素材/<名>_whitebg.png 并返回路径；④ cli.py 用 argparse 收 --input，检查文件和 UAPI_KEY 后调用它。给我 4 个文件的完整代码。」
V2

场景图 —— 白底图 → 多张场景图（S2 出图 + 提示词）

对应阶段：S2 出图；新增构件 2 提示词模板。新增 ARK_API_KEY 依赖。

目标

在 V1 白底图基础上，把商品「原样」放进几个不同场景（如北欧客厅、办公桌、礼品盒），用 Seedream 4.0 各出一张场景图。

你要新增 / 修改的

① 新建 prompts.py
  • DEFAULT_SCENES = ["北欧客厅场景","办公桌使用场景","礼品盒包装场景"]
  • build_scene_prompt(name, selling_point, scene) -> str：返回一段提示词，强调「商品外观须与白底图完全一致、不可变形变色」。
② 改 adapters.py 加 S2
  • 常量：SEEDREAM_ENDPOINT、SEEDREAM_MODEL（默认 doubao-seedream-4-0-250828）。
  • 辅助：_image_to_data_uri(path)、_http_post_json(...)、_http_get_bytes(url)。
  • stage2_scene(white_path, name, selling_point, scene, api_key, prompt_override=None) -> str：以白底图为参考图，调 Seedream 出场景图，存 assets/素材/<名>_scene_<场景>.png 返回路径。
  • generate_image(task, api_key=None, white_path=None) -> dict：统一出图入口，返回 {"ok":True,"path":...,"metrics":None,"cost":...}。
③ 改 cli.py：S1 去底后，遍历 DEFAULT_SCENES 各调一次 generate_image，打印每张结果。
验收： 跑通后 assets/素材/ 下除白底图外，还有 3 张不同场景的商品图；商品在图里不变形、不换色。
向 AI 提：「在现有包上加 V2：新建 prompts.py（DEFAULT_SCENES + build_scene_prompt），adapters.py 加 stage2_scene 和 generate_image（调火山方舟 Seedream 图生图，白底图作参考图），cli.py 在去底后遍历场景各出一张。」
V3

商品页 —— 数据化 SKU + 商品页 + WebP（业务管线）

对应构件：构件 3 任务展开、构件 10 出片交付（含 WebP）、构件 6 Product 类。新增 pipeline.py。

目标

把「一个商品 + 多张场景图」组织成结构化数据（SKU），输出可直接喂给网页的商品页数据（sku.json / sku.js），并把生成图统一压成 WebP 省空间。

你要新增 / 修改的

① 改 schemas.py 加 Product 类（含 score(metrics) 打分方法，V5 才真正用）和 Character(Product) 子类（漫剧角色，更严的打分）。
② 新建 pipeline.py
  • expand_tasks(products)：1 个商品 → 展开成 N 条场景任务（每条带 sku_code/name/scene/status 等）。
  • count_status(tasks)：统计 done/failed/pending。
  • stage_optimize_web(paths)：把 PNG/JPG 转 WebP、限制最大边、删原图，返回旧→新路径映射。
  • deliver(tasks, kept, rejected, product)：按 SKU 分目录归档 + 写 README。
  • write_sku_data(product, all_tasks)：写 deliverables/<sku>/sku.json 和 sku.js（含原图/白底图/各场景图路径）。
  • parse_products_csv(path)：从 CSV 读多个商品（V3 起支持批）。
③ 改 cli.py：构造 product 字典（带 sku_code/name/scenes）→ expand_tasks → run_batch → stage_optimize_web → deliver → write_sku_data。
验收： 输出 deliverables/SKU-001/sku.json 含商品名、卖点、图片列表；生成图均为 .webp；README 写明「AI 合成」合规标注。
向 AI 提：「加 V3：schemas.py 加 Product/Character 类和 score 方法；新建 pipeline.py 实现 expand_tasks、stage_optimize_web（Pillow 转 WebP）、deliver、write_sku_data（写 sku.json+sku.js）；cli.py 串起来。」
V4

识别闭环 —— 照片 → 全自动出全套（S0 智能识别）

对应阶段：S0 识别。至此「照片进去、全套素材出来」完全自动，无需手填商品名。

目标

用豆包视觉模型自动识别照片里的商品、生成上架文案（名称/卖点/建议场景），替代 V3 里手填的商品信息。

你要新增 / 修改的

① 改 adapters.py 加 stage0_recognize(image_path, api_key, model=None) -> dict
  • 把照片转 data_uri，调豆包多模态接口（response_format={"type":"json_object"}）。
  • 返回 {product_name, subtitle, shop_name, points[], tags[], suggested_scenes[]}。
  • 注意解析模型可能用 ```json 代码块包裹，要剥掉再 json.loads。
② 改 cli.py：流程改为 先 S0 识别 → 用识别结果构造 product（scenes 取 suggested_scenes）→ 再 S1 去底 → S2 出图。没 ARK_API_KEY 时明确报错。
验收： 只给一张照片，不手填任何商品信息，程序自动认出商品名、写出卖点、并据此出场景图；sku.json 里的 name/points 来自识别结果。
向 AI 提：「加 V4：adapters.py 加 stage0_recognize，用火山方舟豆包视觉模型识别商品图并返回规定字段的 JSON；cli.py 改成先识别再走 V3 流程。」
V5

工程化收口 —— 质检筛选 + 错误处理 + 归档日志

对应构件：构件 9 质检筛选、构件 5 归档、构件 7 重试、production_log。收尾成「可交付工程」。

目标

让管线具备工程健壮性：个别出图失败不影响整批；跑批结果有日志可溯源；产出有合格/废片区分。

你要新增 / 修改的

① 改 pipeline.py
  • pick_best(tasks, product, threshold=0.7)：按 product.score 把任务分成 kept / rejected；真实模式 metrics=None 时标记 "QC待定" 进 kept（人工/二级复核）。
  • archive_run(tasks, run_dir)：把跑批结果写 deliverables/runs/production_log.csv（跨组交接的凭据）。
② 改 cli.py
  • 加 run_batch(tasks, max_retry=3)：单条失败自动重试，整批不归零。
  • 流程末尾：count_status → archive_run → 对每个 product 调 pick_best → deliver(kept, rejected) → write_sku_data。
验收： 故意断网/坏图制造一次失败，程序不崩、有重试、production_log.csv 记录下来；交付物分合格/废片；README 含废片率与成本统计。
向 AI 提：「加 V5：pipeline.py 加 pick_best（用 Product.score 多态）和 archive_run（写 csv）；cli.py 加 run_batch 重试，流程尾接质检+归档+交付。」
