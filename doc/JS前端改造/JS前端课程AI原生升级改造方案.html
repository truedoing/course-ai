一、本次修订要点（先说结论）

  • 统一母体 = 商品展示（电商素材）：Python 班和 JS 班基础层用同一个案例域——Python 负责「生成商品图 + 商品数据」，JS 负责「把商品数据渲染成可交互展示页」。两课在 Product 数据契约上汇合，基础班案例统一。
  • 原项目八（自制滚动条）、项目九（滑动侧边栏）不再单列：合并为综合项目——商品展示页，原 10+10=20 学时并入综合。滚动条/侧边栏所教的「高级事件」「基础运动」技术不丢，转为综合页里的真实特性（商品轮播、分类侧滑导航）。
  • 基础课层淡化 FDE 表述：一级底座就是「AI 落地执行者」的通用前端训练（读懂/改/调 API + 交付表达），不硬套 FDE 框架名词；FDE 仅作为「二级/三级往上走的方向」一句话带过。
  • 相册→商品图集、商品列表原样保留：项目六多功能相册适配成「商品图集展示」，项目七商品列表本就是商品，直接承接。
  • 新增「首页·某某小店」作为 git 教学入口与可视化外壳：学生在第 0 步 fork 模板 → 改店名/换商品 → 提交，立刻看到自己的小店，获得可视化闭环成果感；后续每个项目都是给这家店加一块功能。它也是两课数据契约的可视化落地壳。
  • 项目一、项目二已讲，从项目三起做切片：一（对话框/输出）、二（计算器/判断）本学期不重做，改造从项目三（循环/商品批量统计）开始。

二、双课统一母体：Product 数据契约

两课能统一，关键不是函数名相同，而是数据模型相同。Python 的 manhua_studio/pipeline.py 里已有完整商品数据链路：parse_products_csv 读入、write_sku_data(product, ...) 写出 sku 数据、deliver(...) 交付图与页。JS 前端直接消费这份数据。

母体一致性的真义：跨课统一的是 Product 数据契约；课内统一的是函数家族——Python 用 build_scene_prompt / write_sku_data / deliver，JS 用 renderProducts / showProduct / calcPrice / collectProduct。所有切片里的字段名、函数名与最终综合案例逐字一致，学生后期零跳变复用。

三、JS 母体设计（展示侧锚点）

JS 主线函数 = renderProducts(products)（项目七·DOM 商品列表），它是所有前置项目的汇合点。项目一~六分别产出它的「零件」，函数名全程不变：

JS 零件函数引入项目作用对应 Python 侧
showProduct(p)项目一 对话框/输出展示单条商品基础信息（名称/价格/卖点）商品数据可视化起点
calcPrice(p, rule)项目二 计算器/判断按会员/满减规则计算最终价price 字段来源
aggregate(products)项目三 循环/统计批量遍历统计库存/总价/分类products 数组遍历
collectProduct(form)项目四 注册页/事件表单录入商品 + 校验parse_products_csv 的反向
openDetail(p) / 多窗体项目五 窗体对象商品详情/编辑窗体商品多视图
showGallery(p.images)项目六 相册→商品图集商品图集轮播（文档对象）images 字段消费
renderProducts(products)项目七 商品列表·DOM汇合：动态渲染商品列表sku 数据落地成页

说明：基础课层不必把 deliver/FDE 挂在嘴边，但零件函数的「读得懂、改得动、接得上接口」正是 FDE 落地执行者的底层能力——二级/三级往上走时再显式接 FDE 框架。
