这个思路我赞成，但理由和你说的不完全一样。"不掺和、管理复杂度低"只对了一半——掺和的代价确实省掉了，但两个营的教师工作量不是 1+1，是 1+1.6。真正支持拆开的，是另外三条更硬的理由。而有一个坑如果不先解决，这条线会在第 6 周无声无息地退化成一次普通的课程设计。下面按"证据 → 判断 → 落地 → 风险"展开。

一、先核对一件事：FDE 这个岗位，专科生够不够得着

这条必须先查，因为它决定训练营对外叫什么名字。实抓 2026 年在招 JD，结论分成两截。

读法：四份大专可投 JD 里，反复出现的不是编程语言，而是三件事——交付到别人手上能用（从 0 到 1 独立交付／现场实施）、写交付文档与验收（安装报告、验收文档）、教会别人用（操作培训、推动普及）。这三件事恰好是传统前端课完全不训练的。

口径决定：内部用 FDE 的方法论，对外用市场认的岗位名

训练营对外名称建议叫"AI 应用与交付"（不叫 FDE 营）。学生简历上写"独立完成 XX 系统从需求到验收的交付"，对应的是深圳 8–18k、绍兴 8–12k 那一档；写"FDE"，对应的是两份本科门槛 JD，会被直接筛掉。方法论是先进的，名字必须是市场认的。

二、为什么这次"共享八成"不成立

之前论证电商与漫剧时用的是同一条判据：两条赛道共享六项工程能力，分叉只在最后 20%。用同一把尺子量 AIGC 与 FDE，结论相反。

2.1 分叉的根源：对手方不是同一个东西

AIGC 对手方 = 机器的不确定性

同一句提示词，跑十次出十种结果。你要做的是在不确定的输出里筛出可用的，并让一千张图看起来像同一个东西。判断对象是产物。

FDE 对手方 = 人的需求不明确

客户说"我要一个能管 XX 的系统"，他自己也不知道要什么。你要做的是把一句含糊的话变成可验收的条目，并在他改主意时活下来。判断对象是人的意图。

由此派生出的能力几乎不重叠：AIGC 练的是废片率、一致性、批量重试、成本核算；FDE 练的是需求澄清、原型、验收签字、培训、沉淀复用。共用的只有调接口、Git、读报错这三件底座——而这三件本来就在第一级语言底座里，两个营各自用各自的语法做一遍即可，不需要协同。

三、管理复杂度：把"一次性成本"和"持续性成本"分开算

你说"不掺和，管理复杂度低"。我把账拆开，因为省下的和增加的不是同一种成本。

拆开后确实省掉的（持续性成本）拆开后新增的（一次性成本）
· 不用每周开契约会
· 不用维护 CONTRACT.md 与字段版本
· 不用调和两边进度（一边卡住另一边空转）
· 不用等对方交付才能开始下一步
· 不用为"他为什么不配合"做思想工作 		· 两套内容（十二周表要写两份）
· 两套判据（验收量表要定两次）
· 两份样品（AIGC 的成片 / FDE 的需求卡样例）
· 两次招募、两份报名表
· 两个客户源（FDE 线需要真实客户，这是新增的最大一项）
净判断

掺和的代价是每周都要为对方让路（持续性），拆开的代价是开学前多备一套材料（一次性）。一次性成本和持续性成本之间，永远选一次性。所以拆是对的——但把它说成"更省事"会误导后面一年的排期，实际是要多备一套东西的。

3.1 一个能省回一半工作量的结构

FDE 线不需要算力。AIGC 线一学期算力账 1.5–2 千元、每次跑批都要盯着额度和失败重试；FDE 线的成本是客户沟通时间，服务器用免费额度即可。这意味着两条线消耗的是两种不同资源，不会互相挤占。

更关键的是：FDE 线的四项能力（需求澄清 F1、原型 F2、培训验收 F5、沉淀 F6）可以直接放进 JS 课内的项目载体，社团只承接与客户直接打交道的部分。上一份文档已论证 JS 课换载体的可行性（同样受"是否教考分离"约束）。课内 + 社团双通道，增量工作量可控。

四、JS 班做 FDE 的三条天然优势

优势一：JS 是 FDE 的母语，不是短板

FDE 交付出去的东西长什么样？一个能点的界面、一套接进来的数据、一份能跑在客户机器上的东西。绍兴那份 JD 直接写"掌握至少一种主流前端技术栈（React、Vue）和后端技术"。让 JS 班去补 Python 批处理管线，等于用短板去打别人的主场；让他们做交付，是把"会做页面"升级为"能让客户把业务跑起来"。

优势二：不需要再解释"为什么不用 Python"

上一份方案里最别扭的一条是——那两个班的 Python 由其他老师按传统教法教，所以社团里只能"只用 JS，不碰 Python"，还要专门跟同事打招呼。改成 FDE 线之后这个矛盾消失了：我们本来就用 JS 做交付，跟他们的 Python 课毫无关系，连解释都不用。

优势三：FDE 自带最真实的对手方，而且比文件契约更真

上一份方案里，为了让"契约有代价"，我设计了一套文件契约（queue/ 与 results/）来制造对手方。那是人造的。FDE 线不需要制造——客户就是对手方，他说"这不对"的时候你不能改字段，你得改理解。三级火箭里最难练的 C4（分工与责任归属）和 C5（交付与对外沟通），在真实客户面前是自动发生的。

五、最大的坑：客户从哪来

这是决定 FDE 线成败的唯一变量

AIGC 线的样品老师自己能做——100 张素材、一条 30 秒成片，花钱花时间就有。FDE 线的客户必须是真人。没有真人客户，三次迭代之后就会退化成"做一个图书管理系统"，和十年前的课程设计毫无区别，学生自己都知道是在演戏，第 6 周开始掉人。

判据：找不到 ≥2 个真实客户，就不要开这条线。推迟一学期，比开一个假营强。

5.1 校内行政就是最好的练兵场

FDE 的正牌岗位要出差、要驻场、要面对合规。这些学生都做不了。但 FDE 的核心动作——听懂需求、做出能用的东西、教会人用、拿到验收——在校内完全可以真做，而且客户质量比想象中高：

客户（校内）可交付的东西为什么适合练
教务处实习台账汇总、毕业设计选题与导师分配、教材征订统计数据真实、规则明确、每年重复（能验证"下次更省事"）
学工／辅导员请假审批流转、资助材料齐套检查、宿舍报修登记使用者多、需求含糊、一定会改主意——正是要练的
招生就业处招聘信息采集与去重、企业对接记录、校友信息维护和就业直接相关，学生有代入感
实训中心设备借用与耗材领用、实训室排期冲突检查规则可判定，容易写出检查项
各系部作品提交与归档、毕业展物料清单工美院校特有，量大且杂
图书馆／后勤研修间预约、报修工单流转有明确使用者，能拿到验收
教师个人成绩录入前的数据清洗、课程素材管理客户就在办公室隔壁，随时能问

客户筛选三条（满足前两条即可）

  1. 人在校内，能见面——不接受"线上提需求"；
  2. 数据能给——一份 Excel 导出就够，不需要开数据库权限；
  3. 使用者 ≥5 人——否则验收没有意义。

第一期只做 2 个客户，且启动会要锁死三件事

  • 需求人本人到场 3 次：启动会（说清楚场景）、中期（看原型）、验收（签单）。三次时间当场写进需求卡，写在纸上的才算约定；
  • 需求人指定一个对接人，不通过第三人传话；
  • 明确"这次不做什么"——这条比"做什么"更能保护学生。

六、FDE 线六个能力项（F1–F6）

与 AIGC 线的 B1–B5 同一套写法：每项写"能做什么 + 可观测证据"，判据分合格／优秀两档。

F1 需求澄清

能做什么把"我要一个能管 XX 的系统"翻译成 5 条可验收条目 + 3 条"明确不做"。
训练任务给一段 3 分钟真实对话记录（第一二次由老师扮演客户，第三次起用真客户），20 分钟内写出需求卡。
交付物需求卡：场景 / 使用者 / 输入 / 输出 / 验收条目 ×5 / 不做清单 ×3。
判据合格 = 5 条里至少 4 条可数可查（"能导出 Excel""10 秒内出结果"），不出现形容词；优秀 = 客户看完说"就是这个"，且没有追问。
最常见的错把客户说的解决方案当成需求。客户说"我要一个下拉框"，真实需求是"别让我填错"。每次复盘都要问一句：他真正想要的是什么。

F2 原型与 Demo

能做什么48 小时内做出能点通的界面，让客户在真实数据之前先看见东西。
训练任务需求卡 → 静态原型（HTML + 假 JSON）→ 当场给客户点。
铁律原型不许接真数据库。先用假 JSON，为的是能一天改三版。接了真数据就舍不得改，这正是课程设计的通病。
判据合格 = 客户自己点完主流程、没提问；优秀 = 客户当场提出 ≥2 条真实修改（说明他真把它当回事了）。

F3 系统对接与数据接入

能做什么读接口文档、把外部数据（表单、表格、公开 API、知识库）变成本地可查的 JSON。
交付物data.json + 字段说明表（每个字段：从哪来 / 是否可能为空 / 什么含义 / 谁在用）。
判据合格 = 字段说明齐全；优秀 = 对空值与异常值有明确处理，且能被下一个人照着接第二个数据源。
对上 JD深圳岗"了解 RAG、向量数据库、Prompt Engineering"——第一年做到"能接一个真实数据源并说清字段"，第二年再碰 RAG。

F4 部署与交付

能做什么让它在别人的机器上跑起来，有安装说明、有回滚办法。
训练任务把项目交给另一组，对方只准看 README，不准提问。
判据合格 = 对方按 README 装起来能跑；优秀 = 装失败时对方能说出失败原因，且 README 当场改好后第二个人一次通过。
对上 JD昆山岗"现场实施和交付""编写安装报告、验收文档"。

F5 培训与验收

能做什么教会非技术用户使用，并拿到书面验收。
训练任务给真实用户做 15 分钟培训 + 一页纸使用说明 + 验收单。
铁律验收单必须由对方写，不能自己写。自己写的验收单等于没验收。
判据合格 = 用户独立完成一次真实任务并在验收单上签字；优秀 = 用户能教会下一个人（说明说明书写得对）。

F6 沉淀与复用 最关键

能做什么把这次做过的东西变成下次能直接用的组件、模板、检查项。
交付物《下次同类项目清单》三件套：可复用组件清单 + 踩坑记录 + 需求澄清问题库。
判据合格 = 下一个项目里至少 3 个东西被直接复用；优秀 = 下一个同类项目交付时间缩短 30%。
为什么它是分界线腾讯研究院《FDE 模式行业观察与实践》（2026-08）给了四层判据：只留给客户一个系统 = 外包；带回经验但无法复用 = 项目制；沉淀为 Skill／模板／测试集 = FDE；显著降低下一次同类交付成本 = 可规模化的 FDE。前五项是"做完"，F6 才是"做成"。

七、两条线在最高层汇合（这是本次最重要的发现）

拆到底之后回头看，两条线并不是完全无关——它们在最高一层汇合，而且汇合点恰好是价值最高的那一层。

这个汇合点可以复用，而且必须复用

AIGC 侧把"这张图行不行"变成检查项，FDE 侧把"这个客户要什么"变成模板——是同一个动作：把一次性的判断翻译成可复用、可交给别人的东西。

所以两条线可以在这一层共用一节联合课（一学期一次即可）：讲"什么叫沉淀"，AIGC 组展示检查项清单，FDE 组展示模板库，互相挑毛病。这节课同时是两条线的最高价值输出，也是唯一值得两边坐在一起的时间。

八、最小共享接口：不掺和，但留四个共用件

完全不往来会失去一样东西——上一份方案里我论证过，"并 JS 进来真正的收益是让工程第一次有了真实对手方"。拆开之后这个收益要找回来一点，但成本必须极低。不共享代码，只共享格式：

共用件内容为什么值得共用
Git 规范与 README 模板一份模板，两边各自填教师只用记一套要求；学生跨线流动时零成本
任务卡五要素格式目标／输入／产出／判据／复盘三问写不出判据的任务不布置——这条铁律两边通用
复盘三问哪里最容易坏？坏了怎么知道？下次改哪？期末答辩三题两边相同，评分尺度一致
失败案例库一个仓库两个目录：aigc/ 与 fde/AIGC 记废片原因，FDE 记需求变更原因——翻对方的目录常有意外收获

8.1 联合答辩：把"真实对手方"找回来

每学期一次，半天，规则极简：

  • AIGC 组展示工具与产线，FDE 组作为真实用户试用，提 3 条修改；
  • FDE 组展示交付的系统，AIGC 组作为真实用户试用，提 3 条修改；
  • 提的修改必须是可判定的（不许"不好看"，要"这一步点了没反应"）；
  • 被提方必须在 48 小时内回应：接受 / 不接受 + 理由。

这一条同时练了 AIGC 侧的 C5（交付与对外沟通）和 FDE 侧的 F5（培训与验收），而且互相是对方最苛刻的用户——因为他们恰好是对对方领域一无所知的人，这是最接近真实客户的评审。

九、FDE 线十二周表（与 AIGC 线并行）

9.1 招募与规模

  • JS 两个班约 60–80 人，FDE 营招 30–40、留 12–15；与 AIGC 营（招 30 留 12）人数相当；
  • 算力几乎为零：FDE 线不用生图生视频，全部走免费额度或本地假数据，一学期账单可忽略；
  • 退出机制同 AIGC 线：连续两周不交退出，每周必须有交付；FDE 线的"交付"从第二周起就是需求卡和原型，不需要写代码也能交。

9.2 分组（4 个岗位位）

岗位位人数负责判据（写死）
客户与需求2–3对接客户、写需求卡、组织验收会拿到客户签字的验收单
界面与交互4–5原型与正式界面客户独立点完主流程不提问
数据与接口3–4数据源接入、字段说明、异常处理字段说明齐全，第二人能照着接第二个源

"交付与沉淀"这一位对应 AIGC 侧的"资产与规范组"，都是接住"不写代码但一直在交付"的那批人。两个营都留这个位置，不是巧合——它就是汇合点的人形。

十一、这条线对课程体系的意义（超出社团本身）

两句话值得单独记下来：

第一句：FDE 线给前端课找到了 AI 时代的落点

前端岗位收缩这件事你早就判断过了。FDE 线给出的答案不是"前端转后端"，而是前端从"写页面"升级为"把 AI 能力交付到业务里"——绍兴那份 8–12k 应届可投的 JD 要的就是"前端 + 后端 + MySQL + Git"的组合，这正好是 JS 课 + 一点拓展就能覆盖的范围。同一批课时，出口换了一个。

第二句：两条线产出两种不同资产

AIGC 线产出作品与产线——可展示、可参赛、可对外讲"AI 内容工业化"。FDE 线产出方法论与案例——真实客户、真实验收、可复用的模板库，对应的是"AI 落地最后一公里"这条叙事。

顺带一个参照：腾讯云在教育行业的 FDE 实践用的是"工作营陪跑"模式——围绕教师真实任务设计闭环，交付的不是培训，而是可运行的应用和可复用的 Skill。你要做的这件事，结构上是同一件事，只是发生在校内。

十二、需要你定的四件事

  1. 客户源：本学期能不能谈到 ≥2 个校内部门？这是开不开这条线的唯一硬前提。建议开学第一周就去教务处、学工、实训中心各谈 30 分钟，只问三件事：有没有一个重复性的表格活、愿不愿意让学生做、能不能来三次会。
  2. 对外名称是否定为"AI 应用与交付"。不建议用 FDE（两份实抓 JD 均要求本科）。
  3. JS 课能否换项目载体（承接 F3 数据接入、F4 部署）——同样取决于是否教考分离。若能换，社团工作量减半。
  4. 是否本期就开 FDE 线，还是先跑一学期 AIGC 线、下学期再开。若第 1 条谈不下来，选后者。
